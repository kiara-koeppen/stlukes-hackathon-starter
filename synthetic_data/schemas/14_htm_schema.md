# Use Case 14 – NextGen HTM Equipment Planning: Synthetic Data Schema

Two synthetic source tables in `hackathon.shared.htm_*`, generated by
`synthetic_data/generators/gen_14_htm.py`. They mirror the shape of the **TMS asset-inventory
export** the Health Technology Management (HTM) team plans replacement from, plus its associated
**work-order** history. **All data is synthetic. No PHI, no real device or network data.**

> This is the natural-language-querying showcase and the Day-1 demo anchor. It is **non-PHI**
> (equipment metadata, not patient data), so it is the one solution safe to project to the whole
> room. Your job: turn a 14,000-row inventory dump into a governed table where an HTM planner can ask
> "What anesthesia machines need replacement in 2026?" and get a trustworthy answer, then forecast
> replacement volume and spend by year, facility, and clinical area.

## Grain summary

| Table | Grain (one row per…) | Source-system analog |
|---|---|---|
| `htm_assets` | asset | TMS asset inventory export |
| `htm_work_orders` | work order | TMS / CMMS work-order history |

`htm_work_orders.asset_number` is a foreign key to `htm_assets.asset_number`. Work orders join to
assets on `asset_number` (keep it a **left join** so an asset with zero work orders still appears).
The dataset is generated "as of" the run date; `end_of_support_date` is deliberately spread across
past / 2026 / future so the headline replacement question returns a meaningful answer.

## `htm_assets` – the asset inventory (the star of the show)

```sql
CREATE TABLE hackathon.shared.htm_assets (
  asset_number          STRING  COMMENT 'Primary key. TMS asset tag, format AST-###### (e.g. AST-004821).',
  description            STRING  COMMENT 'Human-readable asset description (e.g. "Anesthesia Machine - GE Aisys CS2").',
  device_type           STRING  COMMENT 'Normalized device category: Anesthesia Machine, Infusion Pump, Ventilator, CT Scanner, MRI, Ultrasound, Patient Monitor, Defibrillator, Dialysis Machine, Surgical Table, X-Ray, Endoscope.',
  manufacturer          STRING  COMMENT 'Device manufacturer (e.g. GE, Medtronic, Philips, Dragerwerk, Baxter, Siemens).',
  model                 STRING  COMMENT 'Model name/number for this device.',
  serial_number         STRING  COMMENT 'Manufacturer serial number (synthetic).',
  facility              STRING  COMMENT 'Facility where the asset lives (8 St. Luke\'s-style facilities, e.g. Boise Medical Center, Meridian, Nampa, Magic Valley, McCall, Elmore, Mountain Home, Wood River).',
  clinical_area         STRING  COMMENT 'Clinical area / department (e.g. OR, ICU, ED, Radiology, Med-Surg, Cath Lab, Oncology, Dialysis, L&D, Endoscopy, PACU, NICU, Pharmacy).',
  purchase_date         DATE    COMMENT 'Date the asset was purchased/acquired.',
  create_date           DATE    COMMENT 'Date the asset record was created in TMS (usually near purchase_date).',
  end_of_support_date   DATE    COMMENT 'Vendor end-of-support (EOS) date. Deliberately spread: a cohort already past, a large 2026 cohort, and future dates. This is the field that drives the whole use case.',
  vendor_support_notes  STRING  COMMENT 'Free-text vendor service note (e.g. "Vendor confirmed EOS; parts availability limited after 2026", "Service contract renewable annually").',
  operating_system      STRING  COMMENT 'Embedded OS where applicable (e.g. Windows 10 IoT, Windows 7 Embedded, Windows XP Embedded, Linux, RTOS, N/A). NULL/N/A for non-computerized devices.',
  os_eol                BOOLEAN COMMENT 'TRUE if the operating_system is itself end-of-life (Windows 7/XP embedded). A security exposure as well as a support exposure (the Medigate angle).',
  medigate_device_class STRING  COMMENT 'Medigate-imported device classification (e.g. Imaging, Infusion, Respiratory, Monitoring, Lab, Surgical).',
  mac_address           STRING  COMMENT 'Network MAC address (synthetic). Present for networked devices; NULL for non-networked.',
  ip_address            STRING  COMMENT 'Network IP address (synthetic). Present for networked devices; NULL for non-networked.',
  replacement_cost      DOUBLE  COMMENT 'Estimated replacement cost in USD (log-normal by device_type; imaging is most expensive). Drives replacement-spend forecasting.',
  asset_status          STRING  COMMENT 'IN_SERVICE / OUT_OF_SERVICE / PENDING_REPLACEMENT.'
) COMMENT 'TMS asset inventory. ~14,000 synthetic assets across 8 facilities and ~13 clinical areas. Non-PHI. The governed table Genie and the forecast read.';
```

**Design choices engineered into this table (so the demo lands):**
- **End-of-support spread:** roughly 20% already past EOS, a deliberately large ~25% cohort with an
  EOS date in **2026**, and the remainder spread across 2027 and beyond. This is what makes "what
  needs replacement in 2026?" return a satisfying, non-trivial answer.
- **Recognizable device types:** real-sounding categories (anesthesia machines, infusion pumps,
  ventilators, CT/MRI/ultrasound) so natural-language questions feel authentic.
- **OS end-of-life cohort:** a meaningful minority of networked devices run Windows 7/XP embedded
  with `os_eol = TRUE`, so the security-exposure metric has signal.
- **Cost by device type:** `replacement_cost` is log-normal and device-type-aware (an MRI is
  ~$1–3M, an infusion pump ~$2–5K), so replacement-spend forecasting by facility/clinical area is
  realistic and skewed, never flat.

## `htm_work_orders` – maintenance and repair history

```sql
CREATE TABLE hackathon.shared.htm_work_orders (
  wo_id           STRING  COMMENT 'Primary key. Work-order id, format WO-######.',
  asset_number    STRING  COMMENT 'FK to htm_assets.asset_number.',
  wo_date         DATE    COMMENT 'Date the work order was opened.',
  wo_type         STRING  COMMENT 'PM (scheduled preventive maintenance) or Repair (unscheduled corrective).',
  cost            DOUBLE  COMMENT 'Labor + parts cost in USD for this work order (Repairs cost more than PMs; rises with asset age).',
  downtime_hours  DOUBLE  COMMENT 'Hours the asset was out of service for this work order (Repairs drive downtime; rises with asset age).',
  technician      STRING  COMMENT 'HTM technician who performed the work (synthetic name).'
) COMMENT 'TMS/CMMS work-order history. ~5-6 work orders per asset. WO frequency, cost, and downtime correlate with asset age so the support-burden signal is real.';
```

**Correlation engineered in:** older assets (closer to or past `end_of_support_date`) accumulate
**more work orders, a higher share of Repairs (vs PMs), higher cost, and more downtime**. A young
asset is mostly scheduled PMs; an aging one shows the rising repair burden that justifies
replacement. This lets the gold layer compute a meaningful `repair_cost_12mo` /
`downtime_hours_12mo` support-burden signal that feeds `risk_tier`.

## Gold / derived artifacts you will build (in your own group schema, not `shared`)

These are **not** generated – building them is the exercise.

- **`htm_asset_gold`** – one row per asset with derived planning fields:
  - `years_to_eos` – years between today and `end_of_support_date` (negative if past).
  - `is_past_eos` – BOOLEAN, `end_of_support_date < current_date`.
  - `eos_year` – `year(end_of_support_date)`, the grouping key for the 2026 question and the forecast.
  - `wo_count_12mo`, `repair_cost_12mo`, `downtime_hours_12mo` – rolled up from `htm_work_orders`.
  - `risk_tier` – deterministic `CASE` over `is_past_eos`, `years_to_eos`, `os_eol`, and repair
    burden → Critical / High / Medium / Low.
- **Metric Views** – governed KPIs: `past_eos_pct`, `asset_count` and `replacement_spend` by
  `eos_year` × `facility` × `clinical_area`, `eol_os_pct`, `avg_years_to_eos`.
- **`htm_forecast_gold`** – grain `eos_year` (× facility × clinical_area): forecasted replacement
  `asset_count` and `replacement_spend` from `ai_forecast`.

## Suggested build path

1. Land `htm_assets` + `htm_work_orders` in bronze/silver via a Lakeflow pipeline; left-join work
   orders to assets on `asset_number`.
2. Build `htm_asset_gold` with the derived fields – **do the `is_past_eos` / `eos_year` /
   `risk_tier` derivations in gold**, not on the fly in Genie, so every answer is consistent.
3. Define 2–3 Metric Views (percent past EOS, replacement count by year, replacement spend by year).
4. Build the Genie Space over `htm_asset_gold` + the Metric Views; curate instructions, a glossary
   (EOS, PM, HTM), and sample SQL. Get "What anesthesia machines need replacement in 2026?"
   answering cleanly – that is the demo.
5. One `ai_forecast` call → `htm_forecast_gold` for replacement volume/spend by year.
6. A minimal AI/BI dashboard (replacement pipeline + facility/clinical-area heatmap) or an embedded
   Genie panel.
