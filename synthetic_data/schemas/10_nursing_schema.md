# Use Case 10 - Nursing Position Control: Synthetic Data Schema

Five synthetic source tables in `hackathon.shared.nursing_*`, generated by
`synthetic_data/generators/gen_10_nursing.py`. They deliberately mirror the messy multi-source
reality: HR/Power BI roster, TAS scheduling, PTO/LOA events, demand-based staffing metrics, and
budgeted position control. **All data is synthetic. No real employee data.**

> The point of this use case is that the sources do **not** share a clean key. HR uses one ID
> format, TAS uses another plus a free-text name, and some people appear in only one system. Your
> first job is to **reconcile employee identity across the sources** before you can compute or
> forecast anything.

## Grain summary

| Table | Grain (one row per…) | Primary source-system analog |
|---|---|---|
| `nursing_hr_roster` | employee | Power BI / HR roster export |
| `nursing_tas_schedule` | employee × shift × pay_period | TAS time & attendance / scheduling |
| `nursing_pto_loa` | leave event | HR events (PTO / LOA / resignations) |
| `nursing_demand_metrics` | department × shift × pay_period | Enterprise demand-based staffing (Power BI) |
| `nursing_position_control` | department × shift | Budgeted position-control spreadsheet |

Pay periods are bi-weekly, encoded as `YYYY-PPnn` (e.g. `2026-PP12`). The dataset spans several
**past** pay periods (for forecast history) plus several **future** ones (the horizon to forecast).

## `nursing_hr_roster` - the identity source of truth

```sql
CREATE TABLE hackathon.shared.nursing_hr_roster (
  employee_id   STRING   COMMENT 'HR employee id, format E##### (e.g. E04821). Clean canonical key.',
  first_name    STRING   COMMENT 'Legal first name.',
  last_name     STRING   COMMENT 'Legal last name.',
  department    STRING   COMMENT 'Nursing department (e.g. Med-Surg, ICU, ED).',
  unit          STRING   COMMENT 'Unit within department (e.g. 4West, 4East).',
  role          STRING   COMMENT 'Nursing role: RN, LPN, CNA, Charge RN, Nurse Manager.',
  fte           DOUBLE   COMMENT 'Budgeted FTE for this employee (0.0-1.0, some part-time).',
  hire_date     DATE     COMMENT 'Employment start date.',
  term_date     DATE     COMMENT 'Termination date; NULL if active.',
  status        STRING   COMMENT 'ACTIVE / TERMINATED / ON_LEAVE.'
) COMMENT 'HR/Power BI roster. Source of truth for employee identity. Clean E##### ids.';
```

## `nursing_tas_schedule` - scheduling, with intentional identity mismatches

```sql
CREATE TABLE hackathon.shared.nursing_tas_schedule (
  tas_worker_id    STRING  COMMENT 'TAS worker id, format TAS-#### (DIFFERENT format from HR).',
  worker_name      STRING  COMMENT 'Free-text name. Contains variants: nicknames, maiden/married, middle initial, RN suffix, typos.',
  department       STRING  COMMENT 'Department as recorded in TAS (may differ slightly from HR spelling).',
  shift            STRING  COMMENT 'Shift: Day / Eve / Night.',
  pay_period       STRING  COMMENT 'Bi-weekly pay period, format YYYY-PPnn.',
  scheduled_hours  DOUBLE  COMMENT 'Hours scheduled this shift/pay_period.',
  pto_hours        DOUBLE  COMMENT 'PTO hours recorded in TAS for this pay_period (where available).'
) COMMENT 'TAS scheduling. NO shared key with HR: TAS-#### id + free-text name must be fuzzy-matched to hr_roster.';
```

**Reconciliation challenges engineered into this table:**
- `tas_worker_id` is `TAS-####`, not `E#####` - no direct join to HR.
- ~30% of `worker_name` values are variants of the roster name: nicknames (Bob↔Robert,
  Liz↔Elizabeth, Kathy↔Katherine), maiden vs married last name, middle initial inserted,
  `" RN"` suffix appended, and a few single-character typos.
- A handful of TAS workers are **not in HR** (agency/contract staff).
- A handful of HR employees are **not in TAS** (new hires not yet scheduled).
- A few near-identical names sit in different departments, forcing a department tie-breaker.

## `nursing_pto_loa` - effective-dated leave events

```sql
CREATE TABLE hackathon.shared.nursing_pto_loa (
  event_id     STRING  COMMENT 'Surrogate event id.',
  employee_id  STRING  COMMENT 'HR employee id (E#####) this leave applies to.',
  leave_type   STRING  COMMENT 'PTO / LOA / RESIGNATION.',
  start_date   DATE    COMMENT 'Leave/termination effective start.',
  end_date     DATE    COMMENT 'Leave end; NULL for open-ended LOA or resignation.',
  hours        DOUBLE  COMMENT 'Total leave hours (for PTO/LOA); NULL for resignation.'
) COMMENT 'PTO, leave-of-absence, and resignation events. Effective-dated reductions to available FTE.';
```

## `nursing_demand_metrics` - the required-FTE (demand) side

```sql
CREATE TABLE hackathon.shared.nursing_demand_metrics (
  department    STRING  COMMENT 'Nursing department.',
  shift         STRING  COMMENT 'Day / Eve / Night.',
  pay_period    STRING  COMMENT 'Bi-weekly pay period, format YYYY-PPnn (past + future).',
```

```sql
CREATE TABLE hackathon.shared.nursing_position_control (
```

## Gold tables you will build (in your own group schema, not `shared`)

These are **not** generated - building them is the exercise.

- **`emp_crosswalk`** - one row per matched identity: `employee_key` (surrogate), `employee_id`,
  `tas_worker_id`, `match_method` (`EXACT_ID` / `EXACT_NAME` / `FUZZY` / `LLM` / `UNMATCHED`),
  `confidence` (0.0-1.0), `needs_review` (BOOLEAN). This is the crux artifact.
- **`position_control_gold`** - grain `department × shift × pay_period`: `budgeted_fte`,
  `available_fte` (roster minus PTO/LOA/terms plus future hires), `required_fte`, `net_fte`.
- **`staffing_forecast_gold`** - grain `department × shift × pay_period` (future): forecasted
  `available_fte`, `required_fte`, `shortage_fte`, `surplus_fte`.

## Suggested join / reconciliation path

1. Normalize names in both `nursing_hr_roster` and `nursing_tas_schedule` (upper, trim, strip
   `" RN"`, split first/last).
2. **Tier 1 - deterministic:** exact normalized-name + department match → high confidence.
3. **Tier 2 - fuzzy:** rapidfuzz/Jaro-Winkler on name, department as tie-breaker, nickname map for
   Bob/Robert etc. Score → `confidence`; below a threshold → `needs_review = true`.
4. **Tier 3 - LLM (optional):** `ai_query`/`ai_classify` to adjudicate the ambiguous residue only.
5. Left-join everything through `emp_crosswalk.employee_key`; keep `UNMATCHED` rows visible, do not
   silently drop them.
