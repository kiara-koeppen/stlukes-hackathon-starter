# Use Case 06: Hospitalist Scheduling Data Schema

Synthetic source tables for the Hospitalist Scheduling Optimization use case. All tables live in
`hackathon.shared.sched_*` and are **read-only** to every group. Generated by
`synthetic_data/generators/gen_06_scheduling.py`.

> **All synthetic. No PHI.** This data mirrors the *shape* of hospitalist scheduling inputs
> (believed to originate in **Lightning Bolt:** *to confirm* with the Nampa Clinical Scheduling
> Office, plus preference/PTO/rule spreadsheets). It contains no real provider, patient, or HR data.

## The scheduling problem this data encodes

A rolling **28-day block** must be scheduled for ~20–40 hospitalists across day / night / swing shifts
and several units, such that:

- every coverage slot is filled to its required headcount by a credentialed provider (**hard**),
- no provider exceeds max consecutive shifts or minimum-rest rules (**hard**),
- approved PTO is never assigned (**hard**),
- pay / union rules hold (**hard**, parameterized),

while **maximizing** honored preferences and **balancing** nights/weekends fairly (**soft**). The
data is deliberately generated so preferences and coverage are **in tension:** not everyone can get
their first choice, so the preference-vs-equity trade-off is real.

## Tables

### `sched_providers`: the hospitalists
**Grain:** one row per provider.

| Column | Type | Description |
|---|---|---|
| `provider_id` | STRING | Primary key, e.g. `HOSP-0007`. |
| `full_name` | STRING | Synthetic provider name (Faker). |
| `fte` | DOUBLE | Full-time equivalent, 0.5–1.0. Drives target shift count per block. |
| `credentials` | ARRAY<STRING> | Units/service lines the provider is credentialed for (e.g. `["general","icu"]`). |
| `seniority_years` | INT | Years of seniority; senior providers get slightly stronger preference weighting downstream. |
| `service_line` | STRING | Primary service line (`general`, `icu`, `cardiology`, `nocturnist`). |
| `max_consecutive_shifts` | INT | Hard cap on consecutive shifts (typically 6–7). |
| `min_rest_hours` | INT | Minimum rest between shifts (typically 10–12). |
| `wants_night_differential` | BOOLEAN | Eligible/opted-in for night-differential pay. |

### `sched_preferences`: stated scheduling preferences
**Grain:** one row per provider × shift_type × weekday.

| Column | Type | Description |
|---|---|---|
| `provider_id` | STRING | FK → `sched_providers`. |
| `shift_type` | STRING | `day`, `night`, or `swing`. |
| `weekday` | STRING | `Mon`..`Sun`. |
| `preference_weight` | INT | −5 (strongly avoid) .. +5 (strongly want). Soft-objective input. |
| `wants_consecutive` | BOOLEAN | Prefers grouped/consecutive shifts over scattered singles. |
| `max_shifts_per_block` | INT | Provider's own cap on shifts in the 28-day block. |

### `sched_pto_requests`: time-off requests
**Grain:** one row per provider × PTO window.

| Column | Type | Description |
|---|---|---|
| `pto_id` | STRING | Primary key. |
| `provider_id` | STRING | FK → `sched_providers`. |
| `start_date` | DATE | First day off (inclusive). |
| `end_date` | DATE | Last day off (inclusive). |
| `status` | STRING | `approved` (hard block), `requested` (soft, honor if feasible), `denied`. |
| `reason` | STRING | Free text (e.g. `vacation`, `conference`, `family`). **HR-sensitive:** mask for non-scheduler roles. |

### `sched_coverage_requirements`: demand to be filled
**Grain:** one row per date × shift_type × unit.

| Column | Type | Description |
|---|---|---|
| `date` | DATE | Calendar date within the 28-day block. |
| `shift_type` | STRING | `day`, `night`, `swing`. |
| `unit` | STRING | Unit/service needing coverage (`general`, `icu`, `cardiology`). |
| `required_headcount` | INT | How many credentialed providers must be assigned to this slot (hard). |
| `required_credential` | STRING | Credential a provider must hold to fill this slot. |

### `sched_pay_rules`: pay / union / compliance rules
**Grain:** one row per rule. Parameterized so rules are easy to add/adjust.

| Column | Type | Description |
|---|---|---|
| `rule_id` | STRING | Primary key, e.g. `PAY-003`. |
| `rule_type` | STRING | `max_consecutive`, `min_rest_hours`, `night_differential`, `max_shifts_per_block`, `min_shifts_per_block`, `no_night_then_day`. |
| `description` | STRING | Human-readable statement of the rule. |
| `param_name` | STRING | Name of the tunable parameter (e.g. `max_consecutive_days`). |
| `param_value` | STRING | Value as string (cast on read), e.g. `6`, `10`, `true`. |
| `applies_to` | STRING | Scope: `all`, a `service_line`, or a `provider_id`. |

### `sched_existing_schedule`: historical assignments (seed / compare)
**Grain:** one row per historical assignment.

| Column | Type | Description |
|---|---|---|
| `assignment_id` | STRING | Primary key. |
| `provider_id` | STRING | FK → `sched_providers`. |
| `date` | DATE | Date of the assignment (in the block preceding the one being scheduled). |
| `shift_type` | STRING | `day`, `night`, `swing`. |
| `unit` | STRING | Unit the provider worked. |
| `source_system` | STRING | Where it came from; `lightning_bolt` (to confirm) for realism. |

## Tables the *solution* writes (not generated here)

These are produced by a team's solver/app in their **own** schema (e.g. `hackathon.group2_scheduling.*`),
not in `shared`. Documented here so the shape is consistent across teams.

- **`sched_draft_assignments`:** grain: one row per provider × date × shift in the draft.
  Columns: `run_id`, `provider_id`, `date`, `shift_type`, `unit`, `is_hard_ok` (BOOLEAN),
  `why_factors` (STRUCT: preference weight applied, equity contribution, alternatives considered).
- **`sched_solver_run`:** grain: one row per solve. Columns: `run_id`, `solved_at`, `status`
  (`optimal`/`feasible`/`infeasible`), `objective_value`, `constraint_slack` (MAP), `params` (MAP),
  `actor`.

## Relationships

```
sched_providers 1───* sched_preferences        (provider_id)
sched_providers 1───* sched_pto_requests        (provider_id)
sched_providers 1───* sched_existing_schedule   (provider_id)
sched_coverage_requirements  *───* sched_providers   (via required_credential ∈ credentials)
sched_pay_rules  applies_to → all | service_line | provider_id
```

The solver joins `sched_coverage_requirements` (demand) against eligible `sched_providers` (supply,
filtered by `credentials`), subtracts `sched_pto_requests` (approved), enforces `sched_pay_rules`,
and optimizes toward `sched_preferences` + equity.
